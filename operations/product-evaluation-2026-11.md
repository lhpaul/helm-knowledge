## Scope and method

This evaluation inventories where Helm runs, who uses it and how much, what
constrains its integrations, how Fleet and Grok Bot relate to it, and how
[Project #3](https://github.com/users/lhpaul/projects/3) compares with the
roadmap.

Snapshot revisions: `lhpaul/helm` `develop` at `f0cbf4d`, this repo `main` at
`160d914`, `lhpaul/helm-core` `develop` at `579a9db`. Board export taken on
2026-11-13.

Sources, all read-only: this repo, Helm code and GitHub history, Helm Core
pilots, `gh` reads of issues, PRs and Project #3, and the owner's private
operations notes. No running service was called. Consumers are described
generically; private repositories appear only as aggregate counts.

Every finding is labeled:

- **Verified:** checked during this evaluation against code, GitHub data or
  board data, with the date of the check.
- **Recorded:** stated in a dated document (this repo or the owner's notes) but
  not re-checked live, because doing so would mean calling a running service or
  touching a node.
- **Assumption:** an inference that still needs confirmation.

## 4. Integration constraints

1. **Public ingress.** Webhooks need a stable public HTTPS endpoint. Linear
   disables a webhook after failed deliveries and expects an acknowledgement
   within 5 seconds (helm#106). A previous ingress was replaced after resolver
   failures. *Recorded.*
2. **Personal project board.** Project #3 is user-owned, and GitHub does not
   send `projects_v2_item` webhooks for user projects, so board changes reach
   Helm only through a manual sync ([backlog runbook](helm-backlog.md)).
   *Recorded.*
3. **Linear webhook setup.** Creating the webhook through the API needs an
   admin-scoped token; it was configured in the UI (helm#104). *Recorded.*
4. **Secrets.** The service environment is generated from 1Password. The node
   has no durable 1Password session, so regenerating it is a manual step from
   another machine: TD-003 in the [tech-debt register](tech-debt.md), tracked
   as [helm#138](https://github.com/lhpaul/helm/issues/138). *Verified as open.*
5. **Manual, unversioned updates.** The owner pulls and restarts the service
   by hand, and there are no release tags. The running revision is therefore
   not recorded anywhere a reviewer can check, and the board's `released`
   stage does not correspond to a version. *Verified (no tags); revision
   unknown.*
6. **Reviewer dependency on ADF.** Both configs use `local-ai-reviewer`, a
   companion script from the AI Development Framework that must be on the
   server's `PATH` with a logged-in Codex CLI. It is not on `PATH` on the
   node that ran this evaluation, which had to use a temporary clone. Helm's
   review gate depends on an ADF release that Helm does not version. *Verified
   for this node.*
7. **Runtime cost.** The production consumer runs every specialist on Claude
   Code, which is metered API usage (ADR-021), while Helm's own config uses
   Codex. Without a pulse or cost report, spend per item is unknown.
   *Verified (config); cost unknown.*
8. **One service checkout.** The checkout that serves production must not be
   used for development. Agents need isolated clones, and the shared editor
   workspace includes that checkout, so agent sessions do not use it.
   *Recorded.*
9. **Public operational detail.** An existing runbook in this public repo
   contains node-specific operational detail. See decision 7. *Verified.*

## 5. Fleet and Grok Bot

The [Helm Core C8 assessment](https://github.com/lhpaul/helm-core/blob/develop/pilots/2026-10-30-fleet-grok-assessment.md)
(2026-10-30) is the baseline. This evaluation re-checked its follow-ups and
added Helm's side.

### Fleet

- Fleet's node schema accepts the motors `adf` and `helm`. Its readiness check
  does not verify a Helm marker, so a passing check does not prove that Helm
  works on a node. *Recorded in C8.*
- The Fleet issue that assessed a provider-neutral mode for Helm Core was
  closed on 2026-10-30. Its outcome is not recorded in a public document.
  *Verified (closed).*
- The owner's notes describe Fleet as lightly used since early October 2026,
  with Grok Bot used for fast iteration and Fleet as the intended long-term
  runtime. Fleet's first continuous production line started on 2026-11-12 for
  a different project. *Recorded.*
- No evidence shows a Fleet project running the `helm` motor today. *Unknown;
  checking would mean reading node-local configuration.*

**Assessment:** Fleet is not on the critical path of the production consumer
or of Helm development today. A Helm or Core run through Fleet would need,
per node, an isolated checkout, allowed directories, the reviewer companion on
`PATH`, credentials outside the repo, and a validated readiness check.

### Grok Bot

- Two supervised Grok Bot agents use Helm: Helm Dev for `lhpaul/helm` and this
  repo (this session is one of its runs), and the production consumer's
  development agent, which follows Helm's branch conventions. Both open
  sessions only after item-by-item confirmation by the owner. *Recorded.*
- The Helm Dev brief (last updated 2026-10-21) still names CodeRabbit as the
  reviewer and helm#115 as pending. CodeRabbit auto-review is disabled
  (helm#108), helm#115 is merged, and `AGENT.md` requires current-head local
  AI reviewer evidence. A private tracking item opened on 2026-10-30 to fix
  this drift was still open on 2026-11-13. *Verified.* Session prompts already
  carry the current rules, which mitigates the drift.
- The brief keeps Helm Core out of scope, as C8 recommended. *Recorded.*

**Assessment:** Grok Bot is the working path for Helm development today, at
the cost of a brief that must be kept in sync by hand. Changes to briefs or
Fleet belong in their owning repositories and need no change to Helm.

## 7. Decisions for the owner

1. **Self-dogfood.** Should Helm process its own backlog again, or is the
   production consumer the only reference journey? Since August, Helm has
   been changed outside its own orchestrator.
2. **Release and revision policy.** Tag versions and record the revision the
   production service runs, or document that production tracks a hand-pulled
   `develop`.
3. **Board hygiene.** Approve or adjust the actions in section 6, including
   how `Helm Stage` is used for items Helm did not process.
4. **Runtime for Helm sessions.** Keep Helm Dev on Grok Bot, plan a move to
   Fleet, or both. Decide whether Helm Core gets agent coverage, and fix the
   Helm Dev brief drift either way.
5. **Cost measurement.** Implement a minimal pulse or measure runtime spend
   another way before the Core comparison (the production consumer runs on
   metered Claude Code).
6. **Reviewer dependency.** Accept the ADF companion as an external
   dependency with a documented install and version per node, or package an
   equivalent with Helm.
7. **Operational detail in a public repo.** Move node-specific runbook
   content to private operations notes and keep a generic runbook here.
8. **Next Core comparison.** Select the pilot and the comparable Helm journey
   for C7's next step.
